# Запуск TravelApp через Docker Compose

## Запуск

Нужны Docker с Compose v2 (Docker Desktop с WSL integration либо Docker внутри WSL).
Из корня проекта скопируйте пример **на одну директорию выше**, заполните пароли и три разных случайных секрета длиной от 32 байт:

```sh
cp -n .env.example ../.env
# Отредактируйте ../.env, затем:
docker compose --env-file ../.env up -d --build
docker compose --env-file ../.env ps
```

В PowerShell: `if (!(Test-Path ../.env)) { Copy-Item .env.example ../.env }`.
Если `../.env` уже существует, обновите его по примеру, сохранив свои значения.
Сам файл за пределами репозитория не создаётся и не изменяется сборкой или CI.

Compose собирает и запускает семь Java-сервисов, frontend с nginx, четыре PostgreSQL,
Redis и Kafka. Сайт доступен на **http://localhost:8080** (порт задаётся `FRONTEND_PORT`).
Java-сервисы и PostgreSQL доступны только внутри Docker-сети; браузер обращается к API через nginx.
Redis и Kafka дополнительно доступны с хоста на `localhost:6379` и `localhost:9092`, только через loopback.
Зависимости запускаются по healthcheck; для HTTP-сервисов проверяется открытие их порта.
У botservice и notificationservice нет HTTP-порта. Данные PostgreSQL, Redis, Kafka и offset бота сохраняются в named volumes.

Для остановки без удаления данных: `docker compose --env-file ../.env stop`.
Изменение пароля в `.env` не меняет пароль уже созданного пользователя PostgreSQL — это настраивается отдельно.
У каждого Java-сервиса свой `Dockerfile` в каталоге модуля; frontend также собирается отдельно.
Каждая Java-сборка компилирует только выбранный сервис и `sharedlib` (`mvn -pl <service> -am package`).
Контекст сборки — корень репозитория, поскольку Maven нужны родительский POM и общая библиотека.
Runtime работает от непривилегированного пользователя.
Секреты передаются только нужным контейнерам при запуске; `.env` исключён из Docker build context.

Для пересборки одного сервиса: `docker compose --env-file ../.env up -d --build --no-deps tripservice`.

Основной пример настроек — [.env.example](.env.example).
Параметр `--env-file ../.env` обязателен: Compose не ищет файл в родительской папке автоматически.
Настоящий `.env` не нужен CI. Не передавайте его как Docker build argument и не добавляйте секреты в `VITE_*`.

Telegram по умолчанию выключен: без токена сайт работает полностью, а бот и отправка уведомлений не выполняются.
Для Telegram заполните `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_NAME`, `VITE_TELEGRAM_BOT_USERNAME`,
установите `BOT_ENABLED=true`, `NOTIFICATIONS_ENABLED=true` и повторите команду запуска с `--build`.
Username бота включается в frontend при сборке, токен — только в backend при запуске.
Для HTTPS задайте `WEB_SESSION_SECURE=true`; для локального HTTP оставьте `false`.

Внутренние адреса Redis, Kafka и JDBC URL уже прописаны в Compose.
Для запуска Java-сервисов из IDE можно поднять только `redis kafka` с тем же `--env-file`;
настройки адресов на хосте остаются в [.env.infrastructure.example](.env.infrastructure.example).
PostgreSQL и переменные запуска IDE в этом режиме настраиваются отдельно.

## Что использует Redis

Один сервер Redis, ключи с общим префиксом `travelapp:v1:` и отдельными пространствами:

| Данные | Ключ | TTL |
| --- | --- | --- |
| Поиск городов | `cache:weather:cities:…` | 24 часа |
| Текущая погода и прогноз по координатам | `cache:weather:forecast:…` | 10 минут |
| Каталог валют | `cache:currency:catalogue` | 24 часа |
| Курсы базовой валюты | `cache:currency:rates:USD` и т. п. | 1 час |
| Выполнение и результат команды Kafka | `rpc:<service>:<request-id>` | 10 минут |

Кэш общий для всех экземпляров сервиса, сериализация JSON. Ошибки внешних источников не кэшируются.
При недоступном Redis погода и валюты запрашиваются у источника напрямую.
Сессии входа, одноразовые коды Telegram, поездки, расходы и история уведомлений остаются в PostgreSQL.
Права участников не кэшируются: удаление участника и изменение роли действуют при следующем запросе.

## Как общаются сервисы

Внутренние HTTP-клиенты заменены Kafka request/reply:

- botservice → userservice, tripservice, expensesservice;
- tripservice → userservice: проверка существования добавляемого участника;
- expensesservice → tripservice: актуальные участники и права;
- notificationservice → tripservice и userservice: вылеты и получатели уведомлений.

Топики: `travel.rpc.users`, `travel.rpc.trips`, `travel.rpc.expenses`, `travel.rpc.replies`.
Они создаются автоматически. Группа запросов общая для экземпляров одного сервиса;
каждый экземпляр клиента имеет собственную группу ответов, поэтому ответы не теряются между экземплярами.
По умолчанию топик имеет одну партицию; команды обрабатываются по очереди.

В запросе есть UUID, срок действия, операция, тело и учётные данные. Получатель повторно проверяет JWT
(подпись, срок, issuer, audience) или служебный секрет, проверяет поля и вызывает существующие контроллеры/сервисы.
ID пользователя в теле не заменяет личность из JWT. REST сайта остаётся прежним.
Telegram, Open-Meteo и Frankfurter — внешние API; обращения к ним остаются HTTP.

Для команд, которым требуется результат или проверка доступа, вызывающая сторона ожидает коррелированный ответ.
Таймаут — `KAFKA_TIMEOUT_SECONDS=30` (1–90 секунд). Просроченные запросы не исполняются.
Готовые ответы и маркер выполняющейся команды хранятся в Redis; повторная доставка того же сообщения
не создаёт вторую поездку или расход. Изменение тела при том же UUID отклоняется.
Ответ отправляется с подтверждением брокера до фиксации offset запроса.

При недоступном Redis изменения через Kafka **не начинаются**: возвращается 503.
Если результат уже выполненного изменения не удалось сохранить, маркер PENDING предотвращает повторное выполнение.
После таймаута нужно проверить результат просмотром поездок/расходов; автоматически повторять изменение с новым UUID нельзя.
Это не распределённая транзакция PostgreSQL–Redis–Kafka и не обещание exactly-once:
сбой между записью в БД и ответом может оставить результат неопределённым для клиента.
История отправок уведомлений и блокировки в PostgreSQL сохраняют прежнее поведение отправки в Telegram.

## Настройки и эксплуатация

Порты Compose привязаны к loopback, конфигурация предназначена для локальной разработки.
Redis сохраняет AOF и использует `noeviction`: нельзя вытеснять маркеры команд как обычный кэш.
Не очищайте Redis во время обработки команд. Для продакшена задайте пароль/ACL и `rediss://…` для Redis,
SASL/TLS и ACL топиков для Kafka. Для закрытого Kafka-кластера доступны
`KAFKA_SECURITY_PROTOCOL`, `KAFKA_SASL_MECHANISM`, `KAFKA_SASL_JAAS_CONFIG` и стандартное JVM truststore.
Сообщения содержат JWT и служебные данные; payload не должен включаться в журналы.
У топиков короткая политика хранения (5 минут плюс время удаления сегментов).
В production топики обычно создаёт администратор с нужной репликацией и доступами;
после этого задайте `KAFKA_AUTO_CREATE_TOPICS=false`.

`USER_SERVICE_URL`, `TRIP_SERVICE_URL`, `EXPENSES_SERVICE_URL` больше не нужны внутренним Java-клиентам.
Во frontend эти адреса нужны Vite/nginx, поскольку браузер продолжает работать через REST.

## Проверки

```sh
sh ./mvnw -Pci test
cd frontend && npm ci && npm test
```

Workflow [.github/workflows/ci.yml](.github/workflows/ci.yml) запускается на push, pull request и вручную.
Он использует Java 21 и Node 24; Python 3.12 для межсервисных тестов запускается в Docker.
Три задания проверяют unit-тесты, внутрисервисную интеграцию и взаимодействие реальных сервисов.
Профиль Maven `ci` исключает тег `integration`, а `service-integration` выбирает только этот тег.
Отдельный [compose.test.yaml](compose.test.yaml) запускает PostgreSQL, Redis, Kafka,
семь Java-сервисов и Python-тесты; внешние провайдеры заменены локальным HTTP-сервером.
Подробности сценариев и команды запуска — [tests/README.md](tests/README.md).
Временный `.env` создаётся в каталоге runner с фиксированными значениями-пустышками,
его значения экспортируются только на время job, файл удаляется в конце. GitHub Secrets и настоящий `../.env` не используются.
Обычный `sh ./mvnw test` запускает unit- и внутрисервисные Java-тесты.
